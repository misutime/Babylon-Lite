# 模块：设备丢失恢复（Device-Lost Recovery）

> 包路径：`packages/babylon-lite/src/engine/device-lost-*-recovery.ts`、
> `packages/babylon-lite/src/loader-env/environment-recovery.ts`、
> `packages/babylon-lite/src/shadow/shadow-recovery.ts`、
> `packages/babylon-lite/src/sprite/sprite-recovery.ts`，以及
> `packages/babylon-lite/src/text/text-recovery.ts`

## 用途

设备丢失恢复是一项可选启用的、引擎范围的替换设备工作流。每个公共启用器都会向共享的内部协调器注册精确一种渲染上下文类型（rendering-context kind）。协调器重新获取 `GPUDevice`、重新配置所有表面、重建每个已捕获的纹理，然后分派给已启用的类型处理器。如果某个已注册上下文的类型没有对应的已启用处理器，则无法恢复它，因此协调器会使恢复失败，而不是带着它继续运行；绝不会将上下文强制转换为另一种类型。

## 公共 API 接口

```typescript
export interface DeviceLostRecoveryCallbacks {
    onLost?: (info: GPUDeviceLostInfo) => void;
    onRecovered?: () => void;
    onRecoveryFailed?: (error: unknown) => void;
}
export interface DeviceLostRecoveryHandle {
    disable(): void;
}

export function enableDeviceLostSceneRecovery(engine: EngineContext, options?: DeviceLostRecoveryCallbacks): DeviceLostRecoveryHandle;
export function enableDeviceLostSpriteRecovery(engine: EngineContext, options?: DeviceLostRecoveryCallbacks): DeviceLostRecoveryHandle;
export function enableDeviceLostTextRecovery(engine: EngineContext, options?: DeviceLostRecoveryCallbacks): DeviceLostRecoveryHandle;
```

每个启用器涵盖 `engine` 所拥有的每个表面上当前或随后注册的该类型全部上下文；调用方从不传入渲染器实例。通用的 `_enableDeviceLostRecovery` 协调器保持内部私有，不从包根导出。

## 协调器分派

`RenderingContext._kind` 是分派键。公共适配器使用：

| 启用器 | `_kind`           | 枚举的上下文     |
| ------ | ----------------- | ---------------- |
| Scene  | `scene`           | `SceneContext`   |
| Sprite | `sprite-renderer` | `SpriteRenderer` |
| Text   | `text-renderer`   | `TextRenderer`   |

发生设备丢失时，协调器会快照当前活动的注册记录，并将它们归并为每种类型一个处理器。它会停止引擎、验证每个已注册上下文的类型都有对应的处理器、使用原有的特性与存储限制请求一个替换设备、重建引擎存储缓冲区、重新配置每个表面、刷新交换链渲染目标、调整上下文尺寸、重建每个已捕获的纹理、调用每个已注册的类型处理器，并且仅在引擎此前处于运行状态时重启引擎。如果存在某个已注册上下文的类型没有处理器，则恢复失败：让它留在丢失的设备上会导致应用继续运行并针对已释放的原生对象编码绘制命令，这会直接杀死浏览器的渲染进程，而不是产生可捕获的错误。该检查在引擎停止之后、任何资源被销毁或请求替换设备之前运行，因此 `onRecoveryFailed` 触发时引擎仍保持完好，应用可以有意识地丢弃它。回调顺序为：替换前调用 `onLost`，重建完成且恢复第一帧后调用 `onRecovered`，若任何已注册恢复步骤拒绝（reject）则调用 `onRecoveryFailed`。
独立渲染器处理器在场景重建之前运行，以便与场景共享的纹理或字形图集在场景可渲染对象重建绑定之前已经处于最新状态。

对同一类型多次调用会创建独立的句柄和回调。类型级别的启用工作在首次注册时执行；类型级别的禁用工作仅在该类型的最后一个句柄被禁用后执行。`disable()` 是幂等的。Scene 和 Sprite 注册共享一个引用计数的纹理/网格捕获钩子，因此禁用其中一种类型时，只要另一种类型仍需要它，就不会移除捕获。网格几何体保留单独计数，仅在启用 Scene 恢复时生效；仅启用 Sprite 恢复会保留纹理，而不会保留无关的网格数组。

## 资源所有权与重建

### Scene

Scene 恢复仅在启用捕获期间保留网格 CPU 几何体、纹理恢复源以及环境加载器源。其仅在丢失时加载的模块会重建纹理、几何体、骨骼、变形目标、环境光照、阴影生成器、可渲染对象、场景/光源 bind group、帧图任务和渲染目标。

存储支持（storage-backed）网格与可写/顶点/索引/间接存储的自动重建不属于此次集成范围。它们针对恢复的专属注册表、保留源以及句柄刷新通道已被移除，等待后续恢复重新设计。现有的基于 CPU 备份的存储缓冲区钩子仍保留用于普通只读分配。应用必须自行重建受影响的 GPU 角色分配和网格。

环境恢复支持 `loadEnvironment`（`.env`）和 `loadHdrEnvironment`。必须在加载环境之前启用恢复，以便保留 URL/设置源。它会在替换设备上重建镜面反射立方体贴图和 BRDF LUT，同时保持公共 `EnvironmentTextures` 对象标识不变，并安装一个拥有替换纹理的单个场景可销毁对象。加载器拥有的天空盒和地面可渲染对象会在材质组重建之后重新创建，覆盖两个加载器的全部情况：纯色天空盒、地面平面、DDS 立方体天空盒，以及复用光照立方体贴图的 HDR 天空盒。glTF `EXT_lights_image_based` 环境尚未支持恢复；恢复会显式失败，而不是使用过期的设备资源进行渲染。

### 加载器捕获接缝

加载器本身绝不包含恢复语义。`loadEnvironment` 和 `loadHdrEnvironment` 各自仅携带一处基于加载器已计算的局部变量构建的可选链调用 `engine._dlr?.e(…)` / `engine._dlr?.h(…)`。所有语义——什么是恢复源、哪些情况不受支持以及如何重建——都存在于 `device-lost-recovery-capture.ts` 和 `loader-env/environment-recovery.ts` 中，且仅可从 `enableDeviceLostSceneRecovery` 到达。从未启用恢复的应用不会拉入任何这些 chunk。

背景构建器使用它们现有的构建器函数和标量/引用参数通知 `engine._dlr?.c(renderable, builder, ...args)`。仅当捕获实现启用且处于 Scene 恢复启用期间时，才会分配重建闭包并标记 `Renderable._rebuild`。地面构建器会传入 `undefined` 代替其已消耗的图像 Promise，以便恢复时重新获取纹理 URL。当捕获缺席时，没有任何构建器会构造用于恢复的闭包、描述符或参数数组；立方体贴图可渲染对象外壳没有恢复参数或赋值。

恢复过程在遍历 `scene._renderables` 时快照捕获到的 thunk 并按顺序重放它们，这与材质纹理通过 `Texture2D._recoverySource` 恢复的方式相同。`loadEnvironment` / `loadHdr` 路径不携带针对每种背景的恢复代码，背景模块仅保留可选的捕获调用。重放的构建器会经过相同的接缝，因此后续设备丢失仍可恢复。

thunk 是有意设计为不透明的。早期修订版本曾标记一个描述符元组——`[kind, size, rootPosition, url?]`——由恢复流程通过针对 `EnvironmentBackgroundKind` 的四分支 switch 来解释。这会把 `loader-env` 的概念放到 `render/` 最底层的接口上，而避免导入的唯一方法是在每个构建器中把类型写成魔数，这只是向编译器隐藏了依赖，而非消除依赖。使用 thunk 删除了枚举、描述符类型、switch 以及它的四个 `await import()` 调用：每个构建器本身就是一个独立模块，因此重放不需要分派。它也更加正确——元组曾静默丢弃了地面和 DDS 天空盒的 `enableNoise`，而闭包天然捕获了它——并且它能够跨越多次丢失进行组合，因为启用中的捕获会在每次重建背景时标记一个新的 thunk。

`_rebuild` 仅用于没有任何保留结构拥有的可渲染对象。基于网格的可渲染对象继续通过 `scene._groups` 恢复，绝不能同时携带 thunk。这并非历史惯性：一次分组构建会同时生成多个可渲染对象（或将其网格合并为一个），重新运行它还会恢复该组的 `rebuildSingle` 闭包、其 `o` 输出列表以及 uniform 更新器——这些都无法用返回 `Renderable` 的 thunk 来表达。`scene._groups` 是实时状态，已经用于因材质切换和运行时网格添加而重新生成这些可渲染对象，因此恢复流程借用了它，而不是重复实现。如果在同一个可渲染对象上同时设置这两种机制，会导致它被重建两次，并在 `scene._renderables` 中留下重复项。背景之所以需要 thunk，正是因为它们是孤立对象——不基于网格，由加载器直接推入 `scene._renderables`，随后加载器便丢弃了构建它们所用的局部变量。

历史测量数据（在上述仅限 Scene 捕获的契约之前）：最初测量并否决了两种基于捕获的设计。预先描述背景——将加载器的策略输入传递给一个接缝，并在恢复时重新推导规则——会让*每一个*加载环境的场景增加约 65 B。按背景单独捕获（在每个构建器的 `if` 块内部调用 `engine._dlr?.g(...)`）将该开销缩小到约 21 B，但仅适用于构建背景的场景。探索过程最终完全移除了加载器接缝。相对于特性引入前的基线，当时的特性在 73 个场景中测量为 +1,707 B，其中 scene164（恢复一致性场景，也是唯一启用恢复的场景）占 +1,554 B；由于加载器捕获接缝被移除，56 个场景甚至比之前*更小*。11 个构建背景的场景各自为无条件 thunk 支付了 16–56 B。该修订版本倾向于 thunk 的字节成本而非捕获守卫，但仍会在未显式启用时分配并保留仅用于恢复的闭包。当前设计取代了这一权衡：只有启用 Scene 的捕获才会构造背景 thunk；构建器仅保留可选的接缝调用。这些历史数字并非当前设计的测量结果。选择 thunk 而非描述符还将 scene164 的上限需求降低了约 1.6 KB，因为恢复 chunk 不再携带 switch 及其动态导入。

以 `_` 开头的属性名在发布构建中会被混淆（mangled），因此 `_rebuild` 的成本不会高于缩写名称；内部字段采用完整拼写。

捕获绝不能接收分支门控（branch-gating）对象。Rollup 会跟踪对象字面量的属性值，并用它们来证明分支为死代码。传递一个其属性控制可 tree-shaking 代码的对象——例如 `bgOptions`，其 `skipSkybox` / `skipGround` 守卫着加载器对背景模块的 `await import()`——会迫使 Rollup 去优化，因为未知的被调用方可能会修改它。随后它会丢失已知属性值，并在原本已 tree-shake 掉它们的场景中保留 `background-ground.js`（+4,968 B）和 `background-solid-skybox.js`（+1,882 B）。这就是为什么加载器接缝（`_dlr.e` / `_dlr.h`）传递的是已经计算好的标量。背景捕获传递现有构建器及其参数，绝不传递加载器的分支门控选项对象。

阴影生成器在材质组重建之前原地恢复。恢复过程对 `scene.lights` 和 `scene.shadowGenerators` 引用的生成器进行去重，销毁其嵌套的渲染任务状态，重建其设备拥有的纹理、采样器、uniform 缓冲区、管线和 bind group，并保持公共 `ShadowGenerator` 标识不变。目前支持定向 ESM 和 CSM 生成器；对于 PCF，恢复会显式失败，而不是使用过期设备资源继续运行。ESM 仅保留其无法重建的两个模糊标量——`_blurKernel` 和 `_blurScale`，作为内部字段保存在生成器的 `EsmShadowTaskResources` 上——`shadow-recovery.ts` 在仅限丢失时的重建期间从该对象读取它们。保留 `_blurScale` 而不是重新推算为 `mapSize / _blurTexH.width`，是因为并非对所有缩放比例 `blurSize` 都是整数，因此通过纹理尺寸往返推算无法恢复调用方的原始值。其余每个选项均从稳态运行时字段推导：`mapSize`、`bias`、`orthoMinZ`、`orthoMaxZ` 和 `forceRefreshEveryFrame` 来自生成器的 `_config`，而 `darkness`、`depthScale` 和 `frustumEdgeFalloff` 来自其 `_shadowsInfo` 数组。
CSM 直接在原生成器上重新分配深度数组、比较采样器、shadow-params UBO 和 80 浮点接收器 UBO。其配置、CPU 数组、已安装的任务钩子、接收器回调以及运行时启用状态均保持附着在该对象上。替换后的深度数组保留配置的贴图大小和级联数量；已启用的静态缓存也保留 `COPY_DST` 用途。清除嵌套任务状态会使保留的钩子在下次使用时构建新的级联任务。之前借用的接收器 `Texture2D` 保持其标识不变，同时采纳替换纹理、数组视图、采样器和尺寸。在重建后的材质组获取所有权引用之前，恢复会先为生成器获取该替换资源的所有权引用。之后重建材质组时，接收器和投射器仅绑定到替换设备上的资源。

共享的 1x1 PBR 回退纹理在每次恢复时于任何场景重建之前清除一次，因为它是引擎作用域的，且 PBR 回退解析器会惰性重建它——如果按场景清除，会孤立较早场景创建的纹理。因此，仅使用因子和仅接收阴影的 PBR 材质会在替换设备上惰性重建该回退纹理。环境和阴影会在 PBR 组重建之前恢复，以确保其捕获的着色器构建器看到正确的光照和阴影状态。

### SpriteRenderer

Sprite 恢复仅枚举已注册的 `sprite-renderer` 上下文。在重建渲染器状态之前，它会对渲染器使用的每个纹理进行去重并重建：

- 每个图层的图集 `Texture2D`；
- 自定义片元着色器的额外 `Texture2D`；
- 可选的离屏渲染目标。

随后渲染器会重建其共享索引缓冲区以及每个现有的逐图层实例缓冲区、图层 UBO、自定义着色器 FX UBO、bind group、管线引用和渲染 bundle。CPU 实例数组、图层成员资格与顺序、可见性、变换、脏/版本状态、动画钩子、清除设置和目标选择均保持完好。自定义着色器 FX 经过时间会重置为零，因为保留该仅存在于闭包中的累加器会给常规自定义着色器 bundle 增加恢复状态。按设备 keyed 的着色器/管线缓存自然会选择新设备条目。

URL、纯色、位图、动态、原始像素以及空渲染目标纹理仅在启用 Scene 或 Sprite 恢复捕获时才携带纯恢复数据。原始像素更新和运行时图集追加会更新保留的 CPU 副本。在一次成功的 `updateTextureRegion` 队列写入之后，同一个可选 `w` 捕获接缝会接收源 `ArrayBufferView`、目标 x/y/范围、视图相对字节偏移量以及行步幅。只有启用中的捕获模块会将该视图解释为字节，并将每个更新后的 RGBA8 行拷贝到紧凑打包的 `pixels` 源中；填充和所提供视图之外的字节不会被保留。之后的调用方变更不会改变恢复快照。其他源类型不变，且禁用的恢复不会增加任何字节视图分配或保留。应用必须在创建/加载可恢复的精灵纹理之前启用恢复。禁用最后一个使用捕获的句柄会停止为新资源保留源数据；现有的源记录仍保留在其所属纹理上。

动态纹理的创建和上传分别使用 `engine._dlr?.dt(...)` 和 `engine._updateCapturedDynamicTexture?.(...)`。创建接缝接收纹理、尺寸、格式、mip 数量和现有的采样器描述符；仅由捕获构造 `dynamic` 恢复源。更新接缝在 GPU 拷贝成功后接收外部图像以及已计算好的翻转/预乘标志；仅由捕获检查并更新保留的源。在没有恢复时，这两个 API 都不会读取 `_recoverySource`、编码源类型或保留图像。更新接缝仅由恢复可选启用安装，并在禁用捕获后保持安装状态。它仅更新现有的 `dynamic` 记录，在之后重新启用恢复时保留最新成功的上传和标志；它绝不会为在捕获禁用期间创建的纹理创建记录。从未可选启用的引擎仅保留可选调用，绝不检查恢复元数据。

### 已捕获的纹理

仅仅靠可达性（reachability）不足以找到它们。一个带有捕获标记、但在丢失时刻没有任何已注册上下文引用的纹理——例如在一种渲染模式下填充但在另一种模式下闲置的精灵图集页面——对于按类型的遍历是不可见的，在恢复后会继续持有丢失设备的 `GPUTexture`。因此，捕获标记还会以弱引用方式将它标记的每个纹理跟踪在所属恢复状态上，协调器在每次丢失时于表面重新配置之后、任何类型处理器运行之前重建该集合一次，从而使处理器绑定到已经是最新的纹理。按类型的遍历依然保留，用于从未被捕获的纹理。重建以恢复源去重并按设备 keyed，因此无论有多少包装器或遍历路径到达某个源，每次丢失它都只上传一次，`url` 源只获取一次，而随后的另一次丢失会再次重建。弱引用集合在翻倍时进行压缩，绝不低于下限。

从另一个包装器派生的包装器也在同一集合中跟踪。`cloneTexture2D` 和 glTF 采样器路径都会展开一个基础包装器，因此结果会继承 `_recoverySource` 而无需经过标记步骤，同时拥有自己的 `texture` 字段。派生包装器会通知捕获模块，该模块会找到捕获了基础源的恢复状态——以弱引用持有，因此生命周期长于引擎的应用纹理不会钉住该引擎的注册记录——并同时跟踪派生的包装器。独立跟踪每一个包装器，而不是通过其基础包装器去到达它们，这才能够恢复其基础包装器已被垃圾回收的克隆体。第一个被到达的包装器执行重建，其余的采纳其纹理、视图和尺寸；携带自身捕获的采样器描述符的包装器会重建该采样器而非基础包装器的采样器，因此 glTF 采样器包装器能保留自己的环绕和过滤设置。

出于包体积而非行为方面的原因，调用点通过两种方式到达该跟踪机制。持有引擎的调用点直接使用 `engine._dlr` 捕获接缝，这只花一次属性访问且不增加模块依赖。glTF 采样器路径就是其中之一：让 `gltf-sampler-desc` 在运行时导入 `texture-2d`，会将该模块拉入原本懒加载或完全不加载它的 bundle 中，经测量这比该特性本身大得多。`cloneTexture2D` 没有引擎——它是公共 API，glTF 通过 `GltfFeature.wrapTexture` 调用它——因此它调用一个由捕获安装、并在从不启用恢复的场景中保持为 null 且被 tree-shake 掉的模块级钩子。两条路径调用相同的跟踪函数。

所有权和释放是两个独立的问题，恢复流程之所以分开询问，是因为不同类型对此的答案不同。

所有权是延续到替换纹理上，而不是从类型重新推算。重建出来的 `GPUTexture` 最初是无主（unowned）的，因此恢复流程读取旧纹理原本有多少个所有者，并将替换纹理补足到该数量。没有这一步，第一个绑定然后解绑重建纹理的消费者就会在应用仍持有包装器时将其销毁。

补足操作会推迟到每个按上下文的处理器都运行完毕之后，这正是使计数正确而非虚高的关键。恢复流程本身会重新建立一部分丢失前的所有权：`rebuildSceneGpu` 会丢弃网格排队的纹理释放并在重建 bind group 时重新获取引用，而动态纹理重建也会重新获取它自己的引用。如果再把完整的丢失前计数叠加到它们上面，就会把它们恰好重复计算一次，使纹理永久处于过度拥有状态——最终销毁永远不会降到零，于是它永远不会被销毁，且下文中的已释放检查在随后的丢失中对它也永远不会触发。推迟执行无需追踪哪个引用来自哪里：一旦所有处理器运行完毕，仍然缺少的那部分从定义上就是恢复流程自身没有还原的所有权。它也是一个计数而不是单次重新获取，因为一个派生族系可以持有对同一个纹理的多个引用——`cloneTexture2D` 将该配对留给调用方——而仅恢复创建者的引用会导致替换纹理计数偏少，从而下一次释放就会销毁一个仍有兄弟包装器指向的纹理。创建者从未获取引用的类型（`createSolidTexture2D` 和 glTF `uploadTex` 路径）没有需要延续的所有权，也不会获得任何所有权。采纳（adopt）纹理的包装器也不获取引用，正如同 `cloneTexture2D` 在创建时不获取引用一样：它们共享当前所指向纹理持有的引用。

在快照之前先排空网格排队的释放看似是同样的修复，实则不然：对于由单个可渲染对象绑定的纯色或 glTF 上传纹理，唯一的引用就是那个可渲染对象的引用，因此排空会使计数降为零，`releaseTexture` 会销毁该纹理并留下下文所述的零条目，于是接下来对于即将被重新录制的 bind group 使用的纹理就会被跳过重建。

推迟所有权的队列挂载在引擎的恢复状态上，而非模块上，因为丢失 GPU 进程会同时丢失页面上的每一个设备，而每个引擎会按自己的时间线恢复。共享队列会让最先到达其处理器的引擎排空所有引擎的条目，从而在其它引擎的处理器尚未重新获取时就把它们恢复到丢失前的完整计数——这会在跨引擎之间而不是单个引擎内部重新引入上述重复计数问题。按引擎隔离也等于按次隔离，但这只是因为协调器使其如此：恢复流程早在处理器完成之前就把替换设备安装到了引擎上，而此时 `_armedDevice` 仍然指代丢失的设备，因此在该窗口期内启用的注册过去常常会布防（arm）替换设备，丢失它会在同一个引擎上启动第二次运行，共享此队列、引擎的设备和其表面列表。现在 `_recovering` 会在一次运行期间阻止 `arm`。等待并不会丢失任何东西：运行一旦结束就会重新布防，且 `GPUDevice.lost` 是一个 Promise，因此在窗口期内丢失的设备也会向后来的订阅者兑现并紧接着得到恢复。失败的运行会清除该标志而不重新布防，因为引擎可能仍停留在丢失的设备上，布防它会导致恢复无限自旋。该队列通过引擎访问而不是作为参数传递，是因为处理器自身的遍历也会调用 `rebuildTexture2D`，而那些调用点未传递的参数会静默丢弃它们先重建的任何资源的所有权。

纹理是否已被*释放*是针对每种类型都会询问的问题，因为每种类型都能到达该状态——`releaseTexture` 是公共 API，如果纹理的创建者自己没有持有引用，它的第一次调用就会销毁该纹理。重建一个已销毁的纹理会把一个存活纹理交还给应用已经不再使用的包装器，而对于曾经有过所有者的纹理，还会持有一个永远不会被释放的引用。因此恢复流程会跳过它。

这个问题由引用计数映射回答，它区分三种状态：没有条目表示从未有任何对象获取过所有权，正数表示纹理被拥有，零条目表示所有所有者都已释放它且 `releaseTexture` 已将其销毁。`releaseTexture` 会留下零而不是删除条目，这正是区分“已销毁”与“从未被拥有”的关键——无论如何键都是弱引用，因此条目不会滞留任何对象。读取三种状态而不是两种，才让该检查能够覆盖纯色和 glTF 上传纹理：如果把它们无主的稳态当作已释放，就会跳过它们中的每一个，让整个 glTF 场景留在丢失的设备上。

该映射以 `GPUTexture` 为键，而不是以包装器为键，因此一个派生族系共享同一条目，无论恢复先访问哪一个包装器，都会读到已释放状态——无论最终释放是由哪一个执行的，都不会有兄弟包装器重建已销毁的纹理。该状态是在恢复路径上读取，而不是由 `releaseTexture` 记录到包装器上，后者会把记账逻辑塞进每一个场景，无论它是否会恢复。

### TextRenderer

Text 恢复仅枚举已注册的 `text-renderer` 上下文。它会重建每个现有的图层 UBO 和实例缓冲区，使 bind group、管线、上传标记和渲染 bundle 失效，并上传保留的 `TextData` 实例字节。每个被引用的 Slug 曲线/带图集（curve/band atlas）都会从 `GlyphStorage` 现有的 CPU 数组重建。按设备 keyed 的文本管线缓存会生成替换管线和共享四边形缓冲区。图层成员资格、顺序、位置、不透明度、覆盖度 gamma、可见性、`TextData` 槽位布局和字形存储均保持不变。Text 恢复不需要额外捕获，因为这些 CPU 数组本身就是权威的文本状态。

属于调用方的资源在恢复后仍归调用方所有：SpriteRenderer 不会销毁图集、自定义纹理或渲染目标；TextRenderer 不会销毁 `TextData` 或 `GlyphStorage`。

## 惰性重建边界

协调器在稳态 bundle 中仅保留注册、所需特性捕获以及 `device.lost` 监听器。设备丢失时会动态导入 `engine/device-lost-recovery-run`，由其获取并配置替换设备、分派恢复处理器并重启渲染。公共启用器模块仅包含回调连接、类型注册以及少量捕获协调。它们的 `_recover` 回调会使用进一步的动态导入：

- Scene 导入 `engine/recovery-rebuild`；
- Sprite 导入 `sprite/sprite-recovery`，它可能会导入纹理恢复；
- Text 导入 `text/text-recovery`。

包根可以导出全部三个启用器，而不会在无关 bundle 中静态保留 SpriteRenderer、TextRenderer、它们的着色器、管线、纹理重建器或字形图集上传代码。所有模块均具有零模块级副作用；可变缓存在显式调用前保持为 null。

## 状态机 / 生命周期

1. 启用应用希望恢复的每一种上下文类型。
2. 对于 Scene/Sprite，在创建需要保留 CPU/源数据的资源之前启用。
3. 注册上下文并正常渲染。
4. 发生非刻意丢失（或内部测试标记）时，回调触发，并由单一协调器执行设备替换和按类型重建。
5. 使用相同的公共渲染器/数据对象恢复渲染。
6. 独立禁用句柄。现有渲染器会继续渲染，但在其最后一个句柄被禁用后，其类型不再可恢复。

## 测试规范

- 协调器单元测试涵盖混合 Scene/Sprite/Text 注册、重复注册、安全幂等禁用，以及共享捕获生命周期。
- 快速失败（fail-fast）单元测试覆盖存在已注册上下文但其类型没有已启用处理器的情况：错误会列出违规类型（去重并稳定排序），且在销毁任何资源或请求替换设备之前抛出。
- 已捕获纹理单元测试涵盖弱引用跟踪、重建没有任何已注册上下文引用的纹理、将创建后追加的字节恢复到应用仍持有的包装器中、每个源每台设备仅重建一次、派生包装器（包括基础包装器已被回收的，以及携带自身采样器的）、单次共享重建使所有包装器保持在同一个纹理/视图/采样器上、跨所有可恢复类型跳过已释放的纹理（包括单个包装器以及由克隆体执行最终释放的族系）、仍重建未被任何对象释放的无主纹理、每种创建者拥有类型经受一次消费者获取/释放周期、派生族系的第二个引用在重建后依然存活、动态重建自身的引用被计入而非重复翻倍、在重建 bind group 时重新获取引用的处理器留下最终销毁仍可归零的计数，以及两个引擎并发恢复（一个停留在其处理器内部而另一个完成）且各自只结算自己的纹理。
- 一项由协调器驱动的测试丢失一台设备，将运行停泊在其处理器内部，然后启用另一种恢复类型并丢失替换设备。它断言当第一次运行正在进行时，不会在该引擎上启动第二次运行，并且延迟的丢失在第一次运行结束后仍能得到恢复。
- Scene 恢复单元测试在 ESM 阴影生成器下替换设备，并断言其纹理、采样器、UBO、隐藏模糊资源和嵌套渲染任务被重建，同时生成器标识保持稳定，且 PBR 回退在材质组重建之前被清除。
- CSM 恢复单元测试覆盖默认和启用静态缓存的路径、替换设备的深度数组/采样器/UBO 资源、保留的配置与 CPU/钩子/回调/启用状态引用、稳定的借用接收器包装器、缓存复制目标用途、嵌套任务销毁，以及生成器所有权经受一次重建材质获取/释放周期。
- 一个真实丢失浏览器场景涵盖环境光照 PBR、一个定向 ESM 投射器和一个仅接收阴影的接收器。它断言替换设备的环境/回退/阴影资源、保留的环境标识、无未捕获 WebGPU 错误、可信的非纯平输出，以及恢复后至少渲染 50 帧。
- Sprite 单元测试替换一个模拟设备，并断言新的索引、实例、uniform、FX、管线/bind-group/bundle 状态、恢复后的图集/自定义/目标纹理、保留的 CPU/图层状态，以及精确类型枚举。
- 像素恢复测试使用字节、字和 `DataView` 输入、非零视图/相对偏移量、填充行以及随后的调用方变更调用 `updateTextureRegion`。替换设备上的上传必须重现完整的更新后图像；被拒绝的上传不得改变快照，且禁用的恢复不得捕获源。
- 背景单元测试覆盖无恢复、仅 Sprite 恢复、启用 Scene 恢复、重复重建以及禁用捕获下的全部四个构建器。没有捕获时，动态纹理更新甚至不得读取恢复元数据。
- 构建测试验证未可选启用的动态纹理和背景消费者既不保留源编码也不保留重建闭包构造，而显式导入的恢复启用器保留捕获实现。
- Text 单元测试替换一个模拟设备，并断言新的图层缓冲区和 Slug 图集纹理、失效/重建的绑定与 bundle、保留的 `TextData`/图层状态，以及精确类型枚举。
- 现有的 Sprite/Text 渲染器单元测试套件保持通过。
- 当能够在不修改基准图像或 MAD/bundle 上限的情况下练习现有的确定性 Sprite/Text 场景时，优先使用聚焦的浏览器恢复场景。完整一致性测试与 bundle 清单重新生成仍作为显式请求时的 PR 准备护栏。
