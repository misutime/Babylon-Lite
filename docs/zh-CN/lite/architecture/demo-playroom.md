# 示例：The Playroom

> 入口：`lab/lite/src/demos/playroom.ts`
>
> 资源根目录：`lab/public/playroom/`
>
> 源码来源：私有仓库 `BabylonJS/ThePlayroom` 修订版本
> `d22ce23ef308e28d1f8b6598b4c72ea944205925`

## 目的

The Playroom 是完整 Babylon.js 6.0 物理应用的独立 WebGPU/Havok 展示示例移植版。它保留了已创作的儿童房环境、103 个谜题放置项、三次投掷小兔玩法、自由相机推力、弹跳器（popper）连锁反应、得分特效以及完整音效面板。它是一个展示示例而非编号的平价性（parity）测试场景，因此没有黄金基准或 MAD 条目。

## API 接口

该示例不导出任何包 API。其浏览器入口创建场景，并将纯状态传递给独立的子系统函数。索引化的冲量、速度和重置辅助函数位于 `playroom/physics-instances.ts`；它们使用内部的薄实例上下文，不会增加普通物理场景的打包体积。

唯一的额外根导出可选启用函数为：

```ts
function enableHavokThinInstanceAdvancedPhysics(world: PhysicsWorld): void;
```

它在创建 Playroom 刚体之前安装逐实例缩放形状与质量处理逻辑。未启用的使用方仍保留更小的共享路径。

## 已创作世界

`GAME_SCALE` 为 `0.2`。`layout.ts` 中的位置保持为源单位，在展开为矩阵时恰好转换一次。`PLAYROOM_LAYOUT` 包含 103 个顶层放置项：

| 系列（Family）             | 放置数量 |
| -------------------------- | -------: |
| domino                     |       12 |
| stack                      |        1 |
| tower                      |        1 |
| cup                        |        9 |
| bowling ball / pins / ramp |   各 1   |
| cube stack                 |       41 |
| cubes-on-path              |        4 |
| arch                       |       15 |
| popper                     |       16 |
| chess                      |        1 |

样条曲线系列先使用均匀 Catmull-Rom 采样，随后执行源码中的等距分布通道。随机颜色/角度选择使用确定性生成器，以便重玩时恢复完全一致的初始创作条件。

### 源变换真值参照（Source transform oracle）

`tests/lite/fixtures/playroom-source-transforms.json` 是用于修正工作的不可变数值参照基准。它通过只读认证访问 `BabylonJS/ThePlayroom` 修订版本 `d22ce23ef308e28d1f8b6598b4c72ea944205925` 手动生成。该夹具记录了源文件的 Git blob 与 SHA-256 标识、本地资源的 SHA-256 值、导入节点的 TRS 与层级行列式、每次源覆写/烘焙操作、源材质背面剔除设置、选定变换后顶点、非对称三角形绕序、法线、切线手性，以及同时处于原生源空间和对比空间中的全部 1,955 个已创作实例矩阵。源码锁定版本为 Babylon.js Core `6.0.0` 和 Havok `1.0.0`；不接受更新的 Babylon.js 版本作为参照基准。

对比约定使用 `F = diag(-1, 1, 1, 1)` 将源右手系世界精确镜像到 Lite 空间一次：实例矩阵使用 `F * M_source * F`，而烘焙顶点使用 `F * v_source`。源放置项构建按构造函数顺序消耗单一的带种子随机流，包括会影响后续变换抽取的装饰性颜色抽取。绝不会从 `expandPuzzle` 重新生成预期值。

每个导入的资源层级都具有正的有符号行列式。Lite 的合成 glTF 根节点和反射几何体烘焙各自贡献一个负行列式，而交换三角形的第二和第三个索引则提供匹配的绕序反转。经过这一对操作后，所有选定的非对称源三角形和对比三角形都朝向其变换后的顶点法线。

### 资源模板等价性

15 个道具模板保留现有的几何体烘焙，因为独立参照基准已证明它们的位置、索引、法线、包围盒和绕序完全匹配。源分离/克隆操作与 Lite 的仅缩放烘焙之间的表观差异属于允许的内部因式分解差异：最终烘焙后的顶点完全一致。特别是，针对 `arch`（`0.2`）、`archTop`（`0.5,0.5,0.2`）和 `chessboard`（`0.6`）的源替换缩放（replace-scale）操作必须保持替换等价，而不是将导入节点缩放再乘一次。

当网格保留已创作的切线属性时，`getMeshGeometry(mesh)` 会返回该切线属性。在两个重点打包代表中，`scene1` 的 BoomBox 包含并渲染用于法线贴图的已创作切线，而 `scene210` 中采用 POSITION/NORMAL 交错存储的 XMP 立方体没有切线访问器且不调用 `getMeshGeometry`。因此，Playroom 的修正绝不能仅仅因为两个场景都导入了核心 glTF 加载器就让 `scene210` 承担 CPU 切线保留开销。`enableGltfCpuTangents` 仅针对 Playroom 加载且仅当资产声明了切线访问器时安装保留钩子；默认加载器路径不存储任何 CPU 切线引用。Playroom 在加载 `towerGameBlock.glb` 时保留那份必需的源切线载荷，而 `createMeshFromData` 在烘焙后的网格上保留该数组。`bakeTemplate` 在创建新的模板 GPU 缓冲区之前，将切线 X 反射并将切线 W 取反各执行一次。缺失的可选源属性保持缺失；不引入任何合成切线、双面材质、剔除覆写或二次负缩放。

### 精确放置展开

世界创建拥有一个带种子的随机流：

```ts
type PuzzleRandom = () => number;
function createPuzzleRandom(seed: number): PuzzleRandom;
function expandPuzzle(entry: LayoutEntry, random: PuzzleRandom, templates: Readonly<Record<string, ModelTemplate>>): PuzzleBatch[];
```

种子为 `0x504c4159`，全部 103 个条目按源构造函数顺序消耗它。Stack 对每个积木依次消耗旋转、X 抖动和 Z 抖动。源空间旋转噪声为 `random * 0.2 - 0.2`；X/Z 抖动为 `random * 0.5 - 0.5`。随后源空间的积木平移和偏航角（yaw）精确镜像到 Lite 空间一次。

径向塔（Radial-tower）锚点由高度 `7.5 * GAME_SCALE`、宽度 `1.5 * GAME_SCALE`、相对半径 `0.9` 和内部调整值 `0.8` 推导得出。它们的最终 Y 值包含通用的 `0.05` 地面偏移；按顺序排列的七种部件角色在 Lite 场景单位中使用 `0.8`、`0.8`、`1.7`、`2.9`、`2.0`、`2.9` 和 `3.8`。组合俯仰/偏航角（pitch/yaw）在执行 RH 到 LH 相似变换之前先使用源欧拉角 XYZ 组合，因此其四元数交叉项与未反射的偏航/俯仰组合符号相反。

Cup 层级从烘焙后的 `cup` 包围盒推导出半高，并且刻意不叠加样条点 Y 值：层级 Y 为 `halfHeight * 2.011 * (iteration + 1) + 0.05`。Cube-path 实例在每一层交错消耗角度和颜色抽取，从烘焙的立方体包围盒推导垂直间距和底部偏移，并且仅在当前点的所有层级完成后才更新上一个样条点。Cube-stack 颜色每个实例消耗一次抽取。Arch 柱体、拱门和顶部的颜色在其源构建位置处消耗抽取。这些顺序规则既保留了后续随机状态，也保留了可见的逐实例数据。

所有放置矩阵都是缩放为 1 的刚体载体局部矩阵。模板缩放已烘焙到顶点中，因此仅由替代载体因式分解引起的矩阵缩放差异，仅在每个采样世界顶点都完全相同时才可接受。受检的几何体关卡要求全部 31,280 个矩阵标量、原点、基向量、行列式以及选定世界点以 `1e-5 + abs(expected) * 1e-6` 的精度匹配独立夹具。

本地 Babylon.js `6.0.0` 捕获测试框架包含一条有记录的浏览器兼容性垫片：在引擎初始化前将已移除的 `GPUAdapter.requestAdapterInfo()` 桥接到当前的 `GPUAdapter.info` 属性。它不改变场景、变换、着色器或绘制数据。

`lab/lite/playroom-placement-harness.html` 是无物理渲染目标。它加载真实的 Lite 资源路径，安装每个当前薄实例矩阵，在不导入或创建 Havok 的情况下渲染，并且仅发布一份复制的 JSON 标量快照。`tests/lite/integration/playroom/placement.spec.ts` 按稳定的放置/模型/实例键对比该快照，包括几何体包围盒、选定局部/世界顶点与三角形、基向量、行列式、有效管线状态以及完整渲染清单。方向光阴影生成器在真实的仅深度通道中记录相同清单。其初始失败是后续修正任务的刻意回归证据。

源 Spector.GPU 捕获将所有 135 次绘制映射到独立的 64 字节步长矩阵缓冲区。上游 Spector.GPU 不监视 `GPURenderBundleEncoder` 也不序列化渲染包内容，因此正常的 Lite 捕获刻意报告一条不透明的 `executeBundles` 命令和零条序列化绘制，同时保留其着色器、管线、纹理、UBO 和缓冲区资源。Playwright `document_start` 透传观察器在不改变渲染的情况下补充了缺失的证据：它将实际的 `createRenderBundleEncoder`、`setVertexBuffer`、`drawIndexed`、`finish` 和 `executeBundles` 调用记录为复制的标量数据。执行的主渲染包和阴影渲染包各自包含 135 次绘制和 1,955 个实例；两者都将全部 135 个矩阵缓冲区和 31,280 个矩阵标量映射到已发布的无物理 Lite 快照。它们的有效管线全部使用 `frontFace: "ccw"`；源双面 PBR 系列使用 `cullMode: "none"`，而 NME 和默认国际象棋 PBR 系列在两个通道中均使用 `cullMode: "back"`。该观察器不发布任何 GPU 或引擎对象。

物理系统在渲染前将动态道具姿势写入 CPU 薄实例内存块。随后每个材质可渲染对象对其缓存的主渲染包和阴影渲染包所捕获的稳定矩阵缓冲区执行一次受版本门控的每帧上传。因此主渲染与阴影渲染无需重新录制任一渲染包即可消费相同的当前姿势。这是一个时间契约，而不仅是初始放置契约：运行时测试会将中间原生 Havok 姿势、CPU 矩阵、从精确绑定缓冲区进行的 GPU 回读以及两个未更改渲染包的后续执行关联起来。PBR 和 Node Material 系列遵循相同的所有权规则，尽管它们的着色器构建方式不同。

当前 Lite 的位置、法线、索引和非对称绕序采样与所有 15 个源模型匹配。`towerGameBlock` 模板未通过烘焙上传保留其源切线属性，因此所需的反射切线手性有一个专门的失败 GPU 回归用例，而不是用双面渲染掩盖。另外，stack、tower、cup 和 cubes 中的 487 个实例保留了刻意的变换回归。Lite 仅用于测试的 `?capture=1` 模式对于展开的 Spector 管线/资源诊断仍然有用，但不用作正常场景实例化的证明，因为它绕过了不透明渲染包。该证据覆盖无物理的主颜色与阴影通道，而非物理刚体实例化。

`tests/lite/fixtures/playroom-cube-stage-markers.json` 为匹配源的 `cubeStack/000/cube` 和已知物理前回归 `cubes/003/cube` 固定了稳定的首、中、末标识。两个队列的几何体输出和 GPU 消费矩阵一致。后续物理工作必须保留这些 ID，同时记录各自独立检查点：原生创建前、原生创建后/步进前、受控零重力写回以及首次重力/接触；载体、实例、形状局部中心和剥离后的渲染缩放都必须各计算一次。

### 物理与实例对齐

135 个道具批次记录拥有 1,955 个活动渲染实例以及恰好 1,955 个原生 Havok 刚体。地面和四面墙增加了 5 个普通逻辑/原生刚体。持久布娃娃（ragdoll）增加了 10 个普通刚体，使运行中的游戏共有 150 条逻辑记录和 1,970 个原生刚体。这三个计数器由隔离的物理测试框架独立报告；逻辑批次计数绝不被视为原生刚体证明。

每条道具记录保留其稳定的源批次键、渲染实例计数和原生实例计数。在同一条记录内，渲染索引、原生创建索引、碰撞索引、射线投射索引、得分索引和索引化控制索引是同一个稳定标识。源批次形状在这些原生实例之间共享：

- 自动包围盒使用烘焙后对比几何体的中心和完整范围（extents）；domino 保持为中心位于 `(0,0.16,0)`、范围为 `(0.176,0.32,0.042)` 的已创作长方体；
- stack 的烘焙后 `towerGameBlock` 长方体中心位于 `(0,0.15,0)`，范围为 `(0.5,0.3,1.5)`。其源资产缩放 `20` 在创建聚合体之前就已烘焙，因此每个刚体实例缩放为 1 并共享该绝对刚体空间形状；
- 变换后的径向塔仍以原点为中心，范围为 `(0.5,1.5,0.3)`。这些是源代码中显式的绝对尺寸，其资产缩放 `0.2` 同样在创建刚体之前就已烘焙；
- 国际象棋棋盘（chessboard）保留 Babylon.js 6.0.0 聚合体行为：其局部中心为 `(0,0.0260188989341259,0)`，而自动包围盒范围是世界包围盒乘以仍然有效的 `0.6` 载体缩放，得到 `(0.7200000286102295,0.03122267872095108,0.7200000286102295)`。Lite 的渲染将等效的 `0.6` 缩放烘焙到了顶点中，但其碰撞体必须保留观察到的源聚合体刚体空间尺寸，而不能用渲染包围盒替代；
- 保龄球是半径为 `0.5` 的球体；
- arch 柱体使用从 `(0,0,0)` 到 `(0,0.6,0)`、半径为 `0.12` 的源 Y 轴圆柱体；
- 杯子、保龄球瓶、拱门顶部和棋子使用各自烘焙的凸包（convex hulls）；斜坡即使为动态刚体也使用其烘焙的索引三角形网格；
- 每个拱门刚体共享源三盒容器，左右中心为 `(-0.3696,0.2,0)` 和 `(0.3696,0.2,0)`，中间中心为 `(0,0.3,0)`，范围分别为 `(0.3696,0.4,0.4)`、`(0.3696,0.4,0.4)` 和 `(0.3696,0.2,0.4)`。

物理回归测试在四个不同的检查点记录每个稳定的立方体队列：原生创建前夕、创建后但步进前、首次零重力/零速度同步以及首次正常重力接触。每个检查点都会对比完整的有效矩阵、有符号行列式和选定的变换后世界顶点，而不仅是平移量。形状局部中心与实例放置保持分离。首/中/末原生句柄标识保持稳定，针对零号和最后一个实例的索引化控制各自发出一次原生调用，且射线投射/碰撞结果返回相同的索引。该测试框架用透传标量观察器包装真实的 Havok 调用，不发布任何原生对象。

房间使用强度为 `0.6` 的 `childRoom_ibl.env`、六张独立的 `childRoom_1K_*.jpg` 天空盒贴图、强度 `0.85` 的方向光 `(0,-2,-2)`、强度 `0.1` 的半球光 `(0,1,0.5)` 以及一张 2048 分辨率的 PCF 阴影贴图。环境加载后，关闭色调映射（tone mapping），曝光为 `1`，对比度为 `1`，从而保留地毯和道具的原始光照。一个 40×40 的仅阴影接收面作为地面的子节点位于地毯上方 `0.001` 处。它使用现有的 `setShadowOnly` PBR 材质，黑色不透明度为 `0.65`：完全受光的片元是透明的，而投射的阴影会压暗地毯，同时不改变其纹理、曝光或环境光照。它不是投射体、拾取目标或物理刚体，并随其地面父节点一同销毁。不应用任何自定义着色器或节点材质图修改。

地面渲染尺寸为 40×40，位于 Y `0.05`；碰撞范围为中心在 `(0,-0.05,0)` 的 `(600,0.1,600)`。四面不可见墙体中心位于 X/Z `±18`、Y `18`。可移动道具保留乘以 `0.2³` 的源质量、材质摩擦力和恢复系数、网格/凸包/复合形状选择，并初始处于休眠状态。长方体形状通常使用每个烘焙模型的几何体包围盒来确定中心和范围。源创作的 domino `(0,0.16,0)` 与变换后的径向塔 `(0,0,0)` 尺寸保持显式定义，上述 Babylon.js 6 棋盘聚合体的缩放范围行为亦然。因此底部原点的模型坐落在其预期的 Y 平面上，而不会与地板或相邻行相交。

## 材质与资源

所有运行时 URL 都通过 `demoAssetUrl` 相对于入口模块解析。运行时不使用任何 GitHub、snippet、CDN 或旧的 `assets/` URL。本地 NME 图表提供地毯、木块、多米诺骨牌、弹跳器图案和瞄准丝带。重复的嵌入式 NME 图像名称按块 ID 规范化；图像字节无损提取并经过校验和验证。导入的材质保持附加状态，除非源代码显式替换它们。

`lab/public/playroom/asset-manifest.json` 是来源、哈希值、省略项和变换操作的权威记录。再分发基于用户的明确授权。源包的 ISC 声明已记录在案，未对单个资产主张未经核实的许可或版权所有者。

## 布娃娃（Ragdoll）

小兔使用十个 BOX 刚体，分别对应 `root`、双臂、双腿、每只耳朵的两段以及 `head`；质量为 `0.08`，摩擦力 `0.6`，恢复系数 `0`。九个球窝（ball-and-socket）约束将每个刚体连接到其最近的已配置祖先节点。`bunny-rig.json` 记录了源关节索引、静止局部变换、绑定世界变换、尺寸、偏移量和最近已配置父节点。

原应用设置了 `scene.useRightHandedSystem = true`；Lite 使用左手系世界空间。元数据仍保持原始右手系坐标。布娃娃沿 X 轴反射源位置、碰撞体偏移和约束轴，并用该反射对绑定旋转做共轭变换（`F * R * F`，四元数 `(x, -y, -z, w)`）。生成平移量已处于 Lite 世界空间中，因此不进行反射。相对于父节点的关节偏移量使用同一套转换后的坐标系。`setBoneWorldPoseDeferred` 提供 glTF 骨骼所需的最终反射，因此得到的骨骼矩阵为 `F * R_source` 而非 `R_source * F`；对于头部旋转四分之一圈的绑定姿势，这两者并不相同。

`tests/lite/fixtures/playroom-source-ragdoll.json` 记录了使用固定源配置从 Babylon.js 6.0.0 / Havok 1.0.0 测得的原生刚体和关节数据。`playroom-ragdoll-handedness.test.ts` 对照该源数据验证全部十个原生刚体位置、尺寸、惯性张量、材质、九个约束帧，以及静止和旋转后的骨骼姿势。源程序使用无约束的角运动：其角度限制调用已被注释掉。手性转换不会添加限制或修改求解器配置。

一个随世界生命周期存在的物理后回调通过关节当前的刚体旋转来旋转每个碰撞体偏移以恢复关节位置，并根据刚体增量和绑定世界旋转推导出目标关节旋转。每个已配置关节都通过 `setBoneWorldPoseDeferred` 作为绝对骨骼空间世界姿势提交，随后执行一次 `bakeSkeleton`。由于可见蒙皮图元带有 `gameScale` 缩放，姿势位置会除以 `gameScale`；世界姿势 API 提供加载器的手性反射，使图元经过反射的世界矩阵不会将绝对平移再次镜像。未配置的脊柱和耳朵节点继续通过骨骼层级继承自其已配置父节点。源关节轴对于四肢/头部为 Z 轴，对于耳朵为 X 轴。发射时在根节点施加点作用一个活动步长的力，大小为 `500`；不能将其当作大小为 500 的冲量。

布娃娃的对齐契约针对最终蒙皮空间，而非 CPU 覆写映射表。针对相反的 X 方向发射和 Z 向对照，集成测试从主绘制所消费的调色板、逆绑定数据、网格世界矩阵、JOINTS 和 WEIGHTS 重建受根权重影响的可见顶点和已配置关节地标点。在整个飞行和接触过程中，这些世界位置和旋转必须与对应的 Havok 关节匹配，同时不改变刚体轨迹、相机跟随目标或场景独立缓存的主任务和阴影任务。可见的布娃娃克隆体注册为阴影投射体，由 `enableSkeletonShadows` 在其移动时提供实时变形后的包围盒。仅深度阴影绘制绑定与主绘制相同的骨骼纹理和关节/权重缓冲区。Next Kick 和 Replay 保留此网格及其投射体成员身份；物理代理盒和未加载的源模板不是投射体。

全部十个刚体从创建起，历经启动、瞄准、飞行、Next Kick 和 Replay，始终保持 `DYNAMIC` 且禁用节点到刚体的步前同步（prestep）。因此重力和接触会在投掷前将小兔从初始生成姿势降落到地面上，并且无论发射状态如何，随世界生命周期存在的回调在每次物理步进后都会将刚体姿势传递到骨骼。

Kick 仅由单次投掷的 `launched` 标志守卫。它既不恢复缓存变换、也不清除速度或改变运动所有权；它在根节点当前模拟的施加点施加一个大小为 `500` 的源力。Next Kick 和 Replay 将十个现有刚体恢复到初始生成配置并清除其速度，但使其立即保持动态，以便它们再次下落并稳定下来。全部十个刚体标识、九个约束标识以及逐记录计分集合在多次投掷之间保持存活。Replay 在重置世界得分和谜题状态时清除这些计分集合。

## 游戏状态与控制

阶段为 `loading → ready → aiming → watching → ended`，其中 `free` 作为叠加模式保留底层阶段。点击 Play 进入 aiming。Kick 武装弹跳器、启用计分、发射并跟随小兔。前两次投掷后提供 Next Kick；第三次投掷在静止或超出 X/Z ±16 范围后结束。破坏状态与得分资格在各次投掷间保留。十个布娃娃刚体和九个约束贯穿全部三次投掷：Next Kick 将整套刚体重置为缓存的初始生成配置、清除线速度和角速度，并使每个刚体保持 `DYNAMIC`。Replay 是页内重置。它将复制的已创作薄实例矩阵恢复到现有的 CPU 内存块和原生刚体中，清除速度、特效/音频/防抖和得分状态，恢复已弹出的弹跳器，重置现有布娃娃，并直接返回 aiming。网格、GPU 缓冲区、物理刚体、形状、约束、碰撞注册、阴影成员身份和姿势回调在每次重玩中均保留其标识。恢复后的谜题刚体保持受模拟控制，与初始游戏过程一致：当玩家瞄准时，重力和接触仍可唤醒并移动它们。

每个符合条件的刚体/实例仅奖励一次 7 分。接触标识和已得分标志存储在示例注册表中，而非引擎句柄中。

轨道瞄准使用 alpha `-1.25`、beta `1.2`、半径 `1`、目标 Y `0.3`、FOV `0.4π`、近/远裁剪面 `0.002/64`、beta 限制 `0.8..1.75`。15 段弹道丝带使用速度 `10`、重力 `9.81`、宽度 `0.2` 以及源 NME 时间输入。观察阶段将半径缓动至 `2.4` 并跟随根节点。Free 模式在桌面端使用 WASD。物理射线投射选择一个正质量的非布娃娃实例；按住蓄力冲量大小为 `0.0008 × heldMilliseconds`。移动、失焦、指针取消、退出模式或销毁都会取消蓄力。只有当前活动相机拥有输入控制权：游戏模式下附加轨道输入，自由模式下附加自由输入，而在 Play 之前两个控制器均不附加。

### 启动与源 UI 等价性

DOM UI 在不引入 Babylon GUI 的情况下复现了固定版 `BabylonJS/ThePlayroom` 修订版本 `d22ce23ef308e28d1f8b6598b4c72ea944205925`。在 `app_package/src/playgroundRunner.ts` 中，横屏（`1481×691`）或竖屏（`871×1866`）启动画面以 `Image.STRETCH_UNIFORM` 占满整个 GUI 纹理。因此 Lite `<img>` 使用 `object-fit: contain` 填充视口；绝不进行裁剪填充（cover-cropped）。其外层启动层没有颜色或透明度遮挡，因此 WebGPU 画布始终合成在每个透明像素及均匀适配图像之外的区域背后。

源加载控件向右下角对齐，带有 `left = "-2%"` 和 `top = "-2%"`。它是一个正方形，横屏时边长为视口宽度的 15%，竖屏时为 20%：源高度为 `widthFraction × (viewportWidth / viewportHeight)`，解析后与其宽度像素边长完全一致。加载图标变为 Play 按钮后应用相同的像素正方形规则。Lite 将偏移映射为 `right: 2vw; bottom: 2vh`，并在每次尺寸变化时重新计算精确的像素变量。

固定版源码每 10 ms 将加载图像旋转角度改变 `360 / 8` **弧度**，随后重置并在就绪后每 10 ms 将 `time` 增加 `0.02` 同时使用 `cos(time) × 0.5` 弧度。Lite 精确保留这些可观察单位、时间间隔、首个就绪采样（`0.5` 弧度）以及余弦采样；既不将加载步进误解为角度，也不用 CSS keyframes 近似余弦摆动。单个由启动控制器拥有的定时器仅旋转按钮的图像伪元素。它在 loading 到 ready 转换时被替换，并在 Play、错误、销毁或减弱动画偏好时停止；没有任何定时器或额外渲染循环能越过这些边界存活。

游戏控制按钮保留精确的源尺寸和锚点：

- Kick 位于右下角，距底部 2%，边长为 `min(20vw, 40vh)`。
- Next Kick 位于左下角，距底部 2%，边长为 `20vw`。
- Play Again 位于右下角，距底部 7%，边长为 `20vw`。
- Free Mode 位于右上角，边长为 `12vw`。

源顶部居中信息栏使用 Verdana 字体：投掷次数行高 30 px、字号 20 px，带有 `3px 3px 8px #111` 阴影；分数行高 30 px、粗体 24 px `#a09`，带有 `#bbb` 3 px 发光。在 Play 之前，HUD 和包括 Free Mode 在内的所有游戏控件均隐藏。在 watching 阶段，Next Kick 按源码可见但处于禁用状态，直到现有的静止关卡允许下一次投掷。图像控件使用类似源码的 0.95 按下缩放、无障碍名称、键盘激活、焦点环以及触控安全的指针处理。

弹跳器在 kick/free 进入后进入武装状态，当角速度超过 `0.06` 时触发一次，并在半径 `1.6` 范围内施加逐实例线性衰减冲量（力度 `0.096`，两个强力弹跳器为 `0.256`）。已触发的弹跳器刚体会立即隐藏并排除在计分之外，待接触排空完成后停放到场景下方并转为静态。Replay 会使任何排队中的停放操作失效，恢复现有刚体与矩阵，并重新启用弹跳器而无需分配替代对象。

## 特效与音频

本地瞄准图驱动一条不可拾取的双面世界空间丝带。其 15 个分段使用平滑后的相机衍生发射俯仰/偏航角和源弹道拦截方程；而其发射偏移则如源码一样使用当前未平滑的俯仰角。瞄准时，轨道目标以布娃娃根节点为中心，并加上源 `2 * GAME_SCALE` 水平偏移和 `1.5 * GAME_SCALE` 高度，使相机和丝带起点共同跟随小兔当前受重力稳定的姿势。在 Play 之前、小兔飞行期间、游戏结束后以及 Free 模式下，丝带均隐藏。

丝带初始使用退化隐藏位置，一旦存在首条非退化瞄准曲线便上传累计距离 U 坐标。这与源码的首个 `CreateRibbon` 帧匹配，并让已创作图表的 UV 渐变产生覆盖率；后续帧仅更新现有的位置缓冲区。重复的序列化 NME 输入获得不同的 Babylon 风格 uniform 名称（`Float`、`Float1`、...），保留全部六个已创作标量默认值，且图表的 `Time` 输入以秒为单位推进。签入的图表与固定源 snippet `8FCL7N#8` 按字节完全一致（SHA-256 `446e8813b77ec4c497ee9e3f899f560779a7cb9c8db57c4c5c4b11c240d61131`）。其 Alpha 路径为 `FragmentOutput #431.a <- Scale #452`，其中 `Scale #453` 将 `Pow #445(Sin #446(uv.y * Float #449), Float #450)` 乘以 `Alpha #454`，而 `Min #718` 将 `uv.x * Float #456` 与 `Float #719` 取最小值。代入序列化值 `Float #449 = 3.141592`、`Float #450 = 0.4`、`Alpha #454 = 0.25`、`Float #456 = 12` 和 `Float #719 = 1`，精确的片元表达式为 `pow(sin(uv.y * 3.141592), 0.4) * 0.25 * min(uv.x * 12, 1)`。

固定源码捕获生成的 WGSL（`shd_10`，第 78–85 行和第 110–124 行）输出了该表达式，其绑定的 UBO 包含相同的五个值。Lite 捕获生成的 WGSL（`shd_5`，第 48 行）输出了相同的表达式，且专项集成测试检查绑定 UBO 中的全部五个值。序列化材质 Alpha 为 `1`；无论是材质 Alpha 还是 Babylon 源码中的 `mesh.visibility = 0.4` 赋值，都不会作为着色器 uniform 或固定功能不透明度因子出现。源码的 `Mesh.DOUBLESIDE` 复制了 90 个正面索引，因此中心/全长片元达到单面 Alpha `0.25`，并在 180 个索引的绘制中混合两次（等效颜色覆盖率 `1 - (1 - 0.25)^2 = 0.4375`）。Lite 保留该合成方式而非直接乘以图表 Alpha：它保留已创作的 `0.25` 并将反向绕序索引集添加到同一丝带网格中。Alpha 混合对颜色使用 `src-alpha / one-minus-src-alpha`，对 Alpha 使用 `one / one`，保留深度测试，禁用深度写入，并禁用背面剔除。不创建任何替换网格、材质、物理刚体、拾取目标、阴影投射体或逐帧资源。

`pointStar.png`、`flare.png` 和 `confetti.png` 是由场景拥有的世界空间公告板模拟。它们的容量、生命周期、发射速率、尺寸、颜色、圆锥/球体轨迹、重力、角速度和爆发数量均保留源数值；不用 DOM 粒子覆盖层替代场景空间运动。逐帧精灵同步通过一个由特效模块自有的可变描述符写入每个存活粒子，其位置和尺寸数组仅分配一次。`addBillboardSpriteIndex` 立即将这些标量复制到系统的稳定实例内存块中，因此描述符复用不会导致精灵别名冲突，也不会改变粒子几何体、数量、颜色、旋转或生命周期。

28 个活动 MP3 文件涵盖木头/塑料/杯子/球瓶/棋子/多米诺接触、地面撞击、投掷物发射/飞行、得分和弹跳器音效。文件只解码一次；有界声道池提供重叠播放。接触路由匹配双方参与者的源标签，无论事件朝向如何都读取双方的精确实例速度，并根据相对速度平方及垂直地面冲击进行门控。bowling、chess、plastic、cup、wood、domino 和 projectile-ground 音效池保留各自的阈值、防抖、音高和音量规则。主增益为 6，配合源相对增益。音频通过用户手势解锁。不可用的音频会显式报告，且绝不阻塞游戏流程。碰撞回调在其完整生命周期内自有两个速度向量、一个指标对象和匹配存储，而非在每次原生事件时重新创建。配置匹配可以原地重写调用方提供的匹配记录。就绪/声道/投掷物/冷却时间和成对去重检查在读取原生速度之前运行；播放时会再次运行原始检查，从而确保观察器顺序、阈值、音效池选择、时间戳和 8 声道上限保持权威性。对于当前没有任何配置可播放的事件，不执行任何速度读取。

## 生命周期与部署

启动控制器在异步初始化前安装唯一的 resize 监听器、动画所有者和进度观察器。现有的 `installFetchProgress` 句柄仍是唯一的 fetch 包装器；其进度/详情数据集反馈给无障碍实时区域（live-region）播报。无论成功还是失败，`done()` 都会恢复原始的 `fetch` 函数标识。音频加载在构建资产、物理、材质和游戏逻辑的同时写入一个稳定的状态对象。一旦真实世界构建完成，场景即注册一次并启动引擎唯一的渲染循环，使首帧及后续帧在延迟的音频拉取/解码尚未完成时即可在透明加载 UI 背后可见。在游戏从 `loading` 进入 `ready`、发布 `canvas.dataset.ready = "true"` 并启用 Play 之前，必需的加载、游戏构建、场景注册、音频完成（或其显式不可用状态）以及首帧世界渲染必须全部完成。音频引擎、输入路由和已解码缓冲区的所有权跨异步边界增量发布。销毁使用包公共的声源和音频引擎销毁操作；在销毁后才解析完成的资源会立即释放，而不会重新附加。若页面卸载已先销毁游戏，延迟的启动续接也会直接退出而不发布 ready。安装失败时保持透明启动画面合成状态，禁用交互按钮，展示可见警报，并断开启动观察器/监听器。稳定的 dataset 暴露阶段、得分、投掷次数、刚体、约束和弹跳器计数，供无视觉冒烟测试使用，而不暴露场景或原生句柄。

独立文档拥有该场景并在页面导航时释放它；Replay 使用上述子系统重置路径。共享示例打包器将整个 `playroom` 目录复制到扁平包旁，因此 `/lite/demo-playroom.html` 以及任意嵌套的扁平部署路径都能在本地解析 JS、WASM、模型、图表、图像、环境贴图面和 MP3 文件。生成独立 HTML 时，它会将实验室的 `./bundle/demos/`、`/bundle/demos/` 和 `/lite/bundle/demos/` 前缀重写为 `./`，包括 CSS 背景图以及两个响应式启动图片 data 属性。源 HTML 保留其实验室相对路径。`tests/lite/build/demo-site.test.ts` 构建 Playroom 并在不依赖实验室路由别名的情况下，通过 HTTP 在根路径和嵌套部署路径下校验生成的 HTML 资源。使用 `pnpm test:build tests/lite/build/demo-site.test.ts` 运行它。

Replay 不执行任何场景或 GPU 退役操作。在构建期间，每个批次在物理步进开始前捕获其已创作的薄实例矩阵内存块和原生姿势检查点；Replay 使用它们来更新现有的原生实例和保留的矩阵缓冲区。恢复后的刚体具有零线/角速度，并在其正常的受模拟控制激活状态下以休眠启动。这使主/阴影数据包和投射体成员身份保持稳定，同时使重置操作保持同步且对原生和 GPU 资源零分配。

### 生命周期排查测试框架

`lab/lite/playroom-lifecycle-harness.html` 是一个可选的诊断入口，而非生产调试模式。它构建正常的 Playroom 场景，并保持渲染包、真实 Havok 步进、单个 2048 PCF 阴影贴图、特效、音频和 Replay 行为全部启用。测试命令通过复制的 `CustomEvent` 数据跨越页面边界；不在 `window` 上发布任何场景、Havok 或 GPU 句柄。

测试框架的透传观察器记录挂钟帧耗时、JavaScript 帧工作量、固定物理步数、GPU 时间戳结果、原生刚体/形状/约束生命周期、碰撞流排空与阶段、原生 ID 解析、变换轮询、GPU 缓冲区写入、特效描述符写入、活动音频/去重状态以及待处理的世界/GPU 退役。测量指标为累计标量计数器和有界采样。浏览器 CPU 和保留内存分配分析在禁用 Spector 的情况下通过 DevTools 协议单独捕获。正常测试框架使用生产环境的事件 ID 查找。诊断模式仅可在该测试入口内部移除特效粒子，绝不能成为运行时画质降级或生产默认值。

## 验证

- 单元测试：索引化刚体访问；103 个系列的数量、真实几何体/碰撞体包围盒及确定性展开；绑定世界布娃娃映射与关节枢轴；持久的三次投掷/计分/重置行为；相机控制权所有权与蓄力取消；源特效轨迹；双参与者索引化音频路由；清单校验和与本地 URL。
- 构建测试：仅根入口公共类型、单示例运行时资产复制与 MIME 类型。
- 浏览器测试：无视觉就绪/阶段/操作/重置/自由模式/嵌套路径检查。
- 展示：一张经批准的代表性 1280×720 JPG，体积小于 250 KB。

本示例交付不包含本地平价性、性能、全场景套件、黄金基准、MAD 或体积上限更新。
